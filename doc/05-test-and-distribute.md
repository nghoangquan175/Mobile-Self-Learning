# 05 — From dev testing to testers' phones

> Written on 2026-10-29. Dev machine: Windows. Builds use Expo + EAS.

## 1. Two layers of an RN app

| Layer | What | Built by |
|---|---|---|
| **JS** | Your code (screens, logic) → one JS bundle | **Metro** |
| **Native shell** | App entry, Hermes engine, native modules (camera, BLE…), config (name, icon, bundle ID, permissions), signature | **Gradle** (Android) / **Xcode** (iOS, macOS only) |

The shell comes from `android/` + `ios/`, generated by `npx expo prebuild` from `app.json` + `package.json`. `.apk` / `.ipa` are zip files containing that compiled shell (+ the JS bundle in release builds).

| | Native shell | JS comes from | Needs a build? |
|---|---|---|---|
| **Expo Go** | Expo's, fixed set of modules | Metro over LAN | No |
| **Development build** | Yours, your modules + dev tools | Metro over LAN | Yes — again only when native deps change |
| **Release / preview build** | Yours, optimized | Embedded in the app | Yes |

## 2. Phase 1 — Dev testing (no build)

```
   Windows PC                                     Phones (same Wi-Fi)
┌───────────────┐                          ┌──────────────────────────────┐
│ code ─► Metro │ ── JS bundle (LAN) ────► │ Android: Expo Go (scan QR)   │
│ (expo start)  │ ◄─ websocket, reload ─── │ iPhone:  Expo Go (Camera QR) │
└───────────────┘                          └──────────────────────────────┘
        │
        └─ library with its own native code? ─► Expo Go can't run it
                                                ─► development build (own shell, still uses Metro)

```

```

      build .ipa (EAS)

                       └─ External: anyone, ≤ 10,000, first build needs beta review
```

## 5. Signing — Android and iOS

### The basics (same on both)

- **Private key** — **signs**. Only its owner has it.
- **Public key** — **verifies** a signature made with the private key. Anyone may have it.
- **Certificate** — an "envelope" holding a public key + some info, **signed with someone's private key**.

```
SENDER (build machine — the private key never leaves it)
  file ──hash (SHA-256)──► a3f9…   short fingerprint: same file → same hash, 1 byte changed → totally different
  a3f9… ──sign with PRIVATE KEY──► signature
  ship: file + signature + certificate (holding the PUBLIC KEY)

RECEIVER (phone / Apple / Google)
  ① file ──hash again──► a3f9…
  ② signature ──open with PUBLIC KEY from the certificate──► a3f9… (the hash at signing time)
  ③ ① == ② ?
       yes → file not changed on the way + signed by the holder of that private key
       no  → refuse
  ④ trust the certificate itself?
       iOS:     it carries Apple's signature
       Android: it matches the certificate of the version already installed (first install: nothing to compare)
```

### Side by side

| | **Android** | **iOS** |
|---|---|---|
| Key pair (private + public) | You make it (`keytool`, or EAS) | You make it (or EAS) |
| Private key held by | You — never Google | You — never Apple |
| **Certificate** holds | Your public key + your name | Your public key + your team |
| **Who signs the certificate** | **You**, with your own private key (*self-signed*) | **Apple**, with **Apple's private key** — from the **CSR** (your public key + team) you send |
| Certificate valid for | You choose (`keytool -validity`); Google Play needs it valid past **22 Oct 2033** — `10000` days (~27 years) is the norm | **1 year** (Apple Distribution); the provisioning profile expires with it |
| File with private key + certificate | **Keystore** `.jks` | **`.p12`** |
| Extra Apple-signed file | — | **Provisioning profile**: App ID + allowed certificates + allowed devices (dev / ad hoc) + entitlements |
| Build signed with | Your private key | Your private key (+ profile embedded) |
| Uploading to the store | The AAB signed with your keystore — it acts as the **upload key** | A separate **App Store Connect API key** (`.p8` + Key ID + Issuer ID), no 2FA |
| Store re-signs for users | Yes — with the **app signing key** Google keeps | Yes — with Apple's signature |
| App identity | **Package name + signing certificate** | **Bundle ID + Team** |
| Phone trusts the build because | Same certificate as the first install | Apple's signature (Apple's root cert is in every iPhone) |
| Lose the private key | Upload key: Google registers a new one. App signing key you held yourself: app can **never be updated** | Revoke the cert, make a new one, regenerate the profile — annoying, not fatal |
| Secret | Keystore + its passwords | `.p12` + password, API key `.p8` |

### Android only

- **Debug keystore** — a throwaway key for dev builds; the RN template's one is the same everywhere. Testing only, never Play.
- **Google Play: two independent keys** (Play App Signing):

| | **Upload key** | **App signing key** |
|---|---|---|
| What | Your keystore | Generated by Google with the app's first release — not derived from yours |
| Identifies | **You, the uploader**, to **Google** | **The app**, to **users' phones** |
| Checked by | Google, on upload | Android on the phone, on install / update |
| Answers | "Did the app's owner send this file?" | "Is this update from the app already installed?" |
| Held by | You (`.jks` file) | Google (never downloadable) |

### iOS only

- Building needs the `.p12` (or cert + private key) **and** the profile; **uploading** needs the API key.
- Expired cert / profile → ad hoc / dev installs stop launching; App Store / TestFlight builds are unaffected. Renewing the cert doesn't break updates (identity is Bundle ID + Team).

| Path | Who checks **your** signature | What the iPhone checks |
|---|---|---|
| TestFlight / App Store (via Apple) | Apple, on upload — then re-signs | Apple's signature |
| Development / Ad hoc (straight to the phone) | The iPhone | Your signature + profile + its UDID is listed |

## 6. Building in CI (GitHub Actions)

| Option | Where the build runs | Credentials (cert, profile) | Effort |
|---|---|---|---|
| **A. Actions triggers EAS** (`eas build --non-interactive`) | EAS servers — GitHub only starts it | EAS keeps them | Least — just an `EXPO_TOKEN` secret |
| **B. `eas build --local` on a GitHub macOS runner** ← *chosen* | **GitHub's runner** | EAS keeps them, the runner fetches them | Medium — doesn't use EAS build quota |
| **C. Fully on a GitHub macOS runner** (`prebuild` → `xcodebuild` / fastlane) | GitHub's runner | **You**: `.p12`, profile, App Store Connect API key in GitHub Secrets | Most — temp keychain, import cert, install profile, upload via fastlane / `altool` |

- In practice: Expo projects mostly use **A** (or EAS's own GitHub integration); bare RN / native teams use **C** with fastlane + `match`.
- macOS runners cost **10×** minutes on private repos (free on public ones).
- C still needs certificates first — run EAS once to create them, then download with `eas credentials`.
